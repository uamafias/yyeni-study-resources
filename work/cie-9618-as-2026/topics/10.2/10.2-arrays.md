## Arrays: terms, choice, writing and processing

### The terms: index, element, bounds

An array holds a fixed number of elements of one data type under one name, and its terms are worth keeping exactly. The index is the position of an element within the array, and the element is the value stored at that position: in Prices[4], the 4 is the index and Prices[4] is the element - the fourth price - so the index says where and the element says what, and reading Data[i] always names the element at index i. The bounds state the range of valid indices: an array declared ARRAY[1:30] has lower bound 1 and upper bound 30, so its elements are reached by the indices 1 to 30, thirty of them, and no other index names anything. Two consequences follow from the bounds being in the declaration. The size is known before anything is stored, because the count is upper bound minus lower bound plus 1, read from the bounds - which is why LENGTH() has no business here: LENGTH() works on strings, and the array's count is in its declaration, not in a function call. And the structure is fixed for the program's life, because the bounds are stated once and do not move, so an array suits data whose size is known before the run - a week of temperatures, a register of 25 names - and a list that grows during the day needs either a declared size with room to spare or the structures of later topics.

### Choosing 1D or 2D

The choice of structure follows the shape of the data, and the test is how many positions name a value. A shop's twenty product prices are each named by one position - the product's number - so one bound pair suits them: DECLARE Prices : ARRAY[1:20] OF REAL. A class's test marks are each named by two positions - the learner and the test - so two bound pairs suit them: DECLARE Marks : ARRAY[1:25, 1:3] OF INTEGER, where the first index chooses the learner's row and the second the test's column, and Marks[7, 2] is one value: the seventh learner's second test. The shape is the justification, and the wrong shape shows in the addressing: storing the class's marks as three separate 1D arrays means a learner's row is three indexings in three names, and each job crosses arrays; one 2D array makes the row one first index and the column one second, so both jobs - totalling a learner, averaging a test - address the structure the data actually has. The 2D form is the 1D form with a second bound pair, and the addressing is the same habit twice: Marks[7, 2] names the element at row 7 and column 2, just as Prices[4] names the element at index 4.

### Writing array pseudocode

The declaration states the name, the bounds and the type, and everything else follows. A week of temperatures:

```pseudocode
DECLARE Temperatures : ARRAY[1:7] OF INTEGER
```

A grid of rainfall readings, four sites by six days:

```pseudocode
DECLARE Rainfall : ARRAY[1:4, 1:6] OF REAL
```

An element is reached by putting the index where the bounds were, one index per bound pair: Rainfall[2, 3] names the element in row 2 and column 3, and it is set like any variable - Rainfall[2, 3] <- 12.5. Setting every element of a fresh array is the first processing job most programs do, and it is a loop over the bounds:

```pseudocode
DECLARE StockCount : ARRAY[1:50] OF INTEGER
DECLARE Index : INTEGER
FOR Index <- 1 TO 50
   StockCount[Index] <- 0
NEXT Index
```

One loop, fifty elements, one statement: the loop's bounds match the array's bounds, and the body's StockCount[Index] names each element in turn - which is the whole trick of array processing, the loop variable travelling the indices while the array name stays still.

### Worked example: three processes on one array

Take a spaza shop's daily takings, DECLARE Takings : ARRAY[1:10] OF REAL, and run the three standard jobs on it. Total the week's takings:

```pseudocode
DECLARE Day : INTEGER
DECLARE Total : REAL
Total <- 0
FOR Day <- 1 TO 10
   Total <- Total + Takings[Day]
NEXT Day
```

Count the days over 100:

```pseudocode
BigDays <- 0
FOR Day <- 1 TO 10
   IF Takings[Day] > 100 THEN
      BigDays <- BigDays + 1
   ENDIF
NEXT Day
```

Find the busiest day:

```pseudocode
Best <- Takings[1]
BestDay <- 1
FOR Day <- 2 TO 10
   IF Takings[Day] > Best THEN
      Best <- Takings[Day]
      BestDay <- Day
   ENDIF
NEXT Day
```

The three share one skeleton: a loop over the bounds, work done on Takings[Day] inside, a result carried in a variable. What changes is the work - add, count, remember - and that skeleton is what every array process in this course is built from. The two named algorithms are the same habit with a target. A linear search looks for a value when nothing is known about where it sits: examine elements in turn until the element equals the target or the upper bound is passed - the search that assumes nothing about order. A bubble sort puts an array in order by comparing neighbours and swapping those out of order, pass after pass, so the largest values bubble to the end and a pass with no swap shows the work is done. Two habits keep the writing honest in any process: the loop’s bounds should match the array’s bounds, because a loop one short misses an element and one long reads past the end; and the loop variable should be named for what it counts - Day, Hour, Member - because the index is a position in the world the array describes, not a number for its own sake. The three worked examples that follow run the skeleton three ways on real data, and every one can be read aloud against the array it processes: the loop visits each element, the work uses the element, and the result survives the loop - which is the whole grammar of array processing, small enough to check line by line.

### Common errors

Two slips recur. Comparing the index when the element was meant: Index = 7 asks whether the loop is at position 7, whereas Scores[Index] = 7 asks whether the value stored there is 7 - the test is to write Data[i] and read i as the index and Data[i] as the element. And calling LENGTH() on an array: the size comes from the declared bounds, because LENGTH() works on strings - the test is whether it is a string; only then does LENGTH() apply.
