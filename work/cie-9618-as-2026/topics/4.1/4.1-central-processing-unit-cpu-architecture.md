## The Von Neumann model, registers and buses

### The Von Neumann model and the stored program

Almost every computer follows one model, described by Von Neumann. The system has one memory that holds both the program's instructions and its data; a single processor that fetches, decodes and executes those instructions; and input, output and storage devices around them, connected by buses. The idea that carries the model is the stored program concept: a program's instructions are held in memory in the same way as its data, so the processor treats instructions as something to be fetched and obeyed, one after another, from memory. The consequence is generality. Because what the machine does is decided by the contents of its memory, the same hardware becomes a different machine whenever a different program is loaded: the office computer runs payroll in the morning, a game at lunch and a calculation in the afternoon, with nothing rewired, because the program is data that can be changed. Earlier machines were built wired to one task; the stored program is what ended that, and every piece of software in this course rests on it.

### The special purpose registers

Inside the CPU, a register is a small, very fast store, and the special purpose registers each have one fixed job. The Program Counter (PC) holds the memory address of the instruction that will be fetched next - not a count of instructions, but an address, which is why its value is copied to the MAR at every fetch. The Memory Address Register (MAR) holds the address of the location currently being read or written, and the Memory Data Register (MDR) holds the data or instruction travelling between the processor and memory: whatever is read arrives in the MDR, and whatever is written leaves from it. The Current Instruction Register (CIR) holds the instruction now being executed, after the fetch copies it there. The Accumulator (ACC) is where the ALU's working results are held: an addition's total lands in the accumulator, ready for the next operation to use it. The Index Register (IX) holds a base address that indexed addressing adds to, and the Status Register holds flags about the last operation - zero, negative, overflow - which later instructions can test. One further kind of register completes the picture: a general purpose register is one the program may use for its own working values, whereas a special purpose register has a role the program does not choose, so the difference is who decides what the register holds. A working habit for the register questions: name the register, then name its single fixed contents - the PC an address, the MAR an address, the MDR a travelling value, the CIR the instruction being executed, the ACC the ALU's running result - because the register's name is the answer to 'what does it hold', and each answer stays within its own kind of thing.

### ALU, Control Unit and system clock

Three parts of the processor do the work of executing. The Arithmetic and Logic Unit (ALU) computes: it performs the program's arithmetic and logic operations - addition, subtraction, comparisons - places the result in the accumulator, and sets the status flags that describe it. The Control Unit (CU) directs: an instruction sitting in the CIR says what must happen but does nothing by itself, and the control unit decodes it and sends the control signals that make the other components act, telling memory to read, registers to pass their contents, or the ALU to operate. Keep the boundary between the two straight: the control unit is one part of the CPU, not the whole of it - the ALU, the registers and the control unit are all parts, and the control unit's share is the decoding and the signalling. The system clock sets the pace: it generates regular timing pulses, and the CPU's steps proceed in step with those ticks, so a higher clock speed means more ticks per second and more instruction stages completed per second, which is why clock speed is one of the performance factors of the next unit.

### Buses: how the components talk

The components of the Von Neumann model are joined by three buses, and each bus carries one kind of thing. The address bus carries memory addresses: when the processor wants a location, the address travels on this bus. The data bus carries the actual data and instructions - the value read, the value written, the instruction fetched. The control bus carries control and timing signals, such as read and write, that tell each component what to do with what is on the other buses. Every memory access uses all three, in the same pattern: the address goes out on the address bus, a read or write signal goes out on the control bus, and the value travels on the data bus. The widths of the buses matter as much as their jobs. A wider address bus carries a larger address, so it can address more memory; a wider data bus moves more bits per transfer, so a 32-bit data bus moves 4 bytes in one transfer and a 64-bit bus 8. Both widths feed the performance story of the next unit, because they set how much the system can address and how much moves at once. A bus question to be ready for: which bus carries what? Answer by naming what travels - an address, a value, or a command - and the bus follows, because the three buses divide the traffic by kind and never share it.

### Worked example: one memory read, bus by bus

Trace the read of a value the processor needs, using every part of this unit. The processor places the address of the wanted location in the MAR. On the address bus, that address travels from the MAR to memory. On the control bus, a read signal travels with it, telling memory what to do. Memory finds the location and places its contents on the data bus, which carries the value back into the MDR. Now the value is inside the processor, ready to be used. Three buses, three jobs, and nothing travels on the wrong one: the address is an address, so it goes on the address bus; the read command is a signal, so it goes on the control bus; the value is data, so it comes home on the data bus. Test any described transfer the same way - name what travels, and the bus names itself.

### Common errors

Three slips recur here. Giving the program counter a counting job: the PC holds the address of the next instruction to be fetched, and the test is that its value is copied to the MAR at every fetch, because the MAR must hold an address. Describing the whole CPU when the control unit was asked for: the control unit decodes and signals, while the ALU computes and the registers hold - remove the ALU and the registers, and what is left is the CU's job. And putting data on the control bus: data and instructions travel on the data bus, addresses on the address bus, and signals such as read and write on the control bus, so the test is to name what travels.

### Where this connects

The registers and buses here are the stage on which the Fetch-Execute cycle of 4.1.2 runs, and the same registers are addressed by the assembly language of 4.2. The gates of 3.2 are the ALU's building blocks, and the memory of 3.1 is what the buses reach.

## Performance, ports, the F-E cycle and interrupts

### What makes a computer fast

A system's performance is the sum of several factors, and each works its own way. The processor type sets what one core can do per tick. The clock speed sets the ticks: more pulses per second means more instruction stages complete per second. The number of cores sets how much runs at once: two cores can execute instructions from two programs simultaneously, so a computer running several programs progresses on them together - though a single program does not speed up unless it is written to split its work across the cores, which is why more cores do not multiply one program's speed. The bus widths set the traffic: a wider data bus moves more bits per transfer and a wider address bus reaches more memory. Cache memory sets the waiting: it holds a copy of the instructions and data the processor is most likely to need next, and a cache hit is reached far faster than a main-memory fetch, so the more of the work that is already in cache, the fewer the slow fetches that interrupt it. When a buyer is offered a faster clock or more cache for the same money, the trade is exactly this list: ticks, width, copies held close. And the honest caveat that answers any performance claim: the factors work together, so a fast clock starved by a narrow bus, or a big cache fed by a slow disk, delivers less than its best number suggests, because the system runs at the pace of its slowest contributor. A performance answer that names one factor and its effect is half an answer; a full one says what the factor changes and what could still hold it back.

### Ports and peripherals

Peripherals attach through ports, and a port is a physical connection with a standard that says what it carries. USB connects a wide range of peripherals - a keyboard, a storage device, a printer, a camera - and devices can be attached and detached while the computer runs, which is why USB is the everyday connection for peripherals of every kind. HDMI carries digital video and audio to a display on one cable: the picture arrives as sent, and the sound arrives with it. VGA, the older standard, carries analogue video signals only: the computer's digital picture must be turned into analogue before the cable and back to digital inside the display, and any sound needs a separate connection. Choosing between them is choosing what the display can take: a digital display with an HDMI port takes HDMI, because the two conversions are avoided and the sound rides along. In practice a room of mixed equipment answers the choice question on its own: a new projector with an HDMI socket takes the laptop's HDMI cable, while the school hall's older projector with its blue VGA socket takes the analogue cable and a separate audio lead, because the port on the display is what the connection must fit.

### The Fetch-Execute cycle

The processor's whole life is one cycle, repeated: fetch an instruction, decode it, execute it. Fetch first, in register transfers, each written as the notation says - square brackets mean 'contents of', and two pairs mean 'contents of the address held in':
[MAR] ← [PC]  the address of the next instruction is copied to the MAR
[PC] ← [PC] + 1  the counter moves on to the following instruction
[MDR] ← [[MAR]]  the instruction at the addressed location is read into the MDR
[CIR] ← [MDR]  the instruction is copied to the CIR, ready to be decoded
Decode second: the control unit interprets the instruction now in the CIR and sends control signals to prepare what it needs - operands fetched, registers opened, memory ready. Execute third: the instruction is carried out - the ALU performs an arithmetic or logic operation and places the result in the accumulator, or a value moves between registers or memory. During the fetch of every instruction the processor checks for interrupts, and an enabled interrupt is serviced before the next instruction is fetched, which is where the cycle meets the last part of this unit.

### Worked example: one instruction through the cycle

Take the instruction ADD: add the value at a memory location to the accumulator. Fetch: [MAR] ← [PC] puts the instruction's address in the MAR; [PC] ← [PC] + 1 moves the counter on; [MDR] ← [[MAR]] reads the ADD instruction itself into the MDR; [CIR] ← [MDR] copies it to the CIR. Decode: the control unit reads the CIR, sees an ADD and the address of its operand, and sends signals that fetch the operand's value from memory into the MDR. Execute: the ALU adds the MDR's value to the accumulator's, places the total back in the accumulator, and sets the status flags - zero if the total is zero, negative if it carries the sign bit. Then the cycle starts again on the instruction the PC now points to. Every instruction the processor has ever obeyed, from a payroll run to a game, went round this loop one line at a time.

### Interrupts

The processor would waste its life waiting if input had to be asked for. An interrupt is a signal that makes the processor pause its current program, run an interrupt service routine (ISR) for that interrupt's cause, and then resume the interrupted program exactly where it left off. The causes are many and each has its own routine: input arriving, such as a key press that needs the key read; a timer expiring, such as a two-minute reminder to save a document; a hardware fault, such as a printer out of paper; and a program error or a program's own request for service. When an interrupt arrives, the processor checks its priority before servicing it, because some events must be answered at once and others can wait their turn. The check happens during the fetch of every instruction, so the response follows closely behind any event, and the interrupted program resumes with its registers intact - the pause is invisible to it, which is what makes interrupts the everyday mechanism for responsiveness. Applications follow from the mechanism: a document that saves itself every few minutes is a timer interrupt at work; a keyboard that never drops a letter is a key-press interrupt serviced before the next instruction; a printer that reports its own paper outage is a fault interrupt - each a cause, a routine, and a return to the interrupted work.

### Common errors

Two slips recur in cycle and interrupt questions. Writing [MDR] ← [MAR] for the fetch's read: that copies the address itself into the MDR, while the fetch needs the value stored at that address, written [MDR] ← [[MAR]] - the test is that two pairs of brackets mean 'contents of the address held in'. And giving one routine every interrupt: each cause of interrupt carries its own service routine, and the processor checks the priority before servicing - the test is to ask whether a printer out of paper and a key press need the same code, which they do not.

### Where this connects

The cycle this unit describes is what the assembly language of 4.2 drives instruction by instruction, and the bit operations of 4.3 are what the ALU performs in the execute stage. The operating system of 5.1 is the program that decides which program's instructions the cycle fetches next, and the interrupt mechanism is one of its tools.
