## Files: keeping data after the program ends

### Why files are needed

Everything met so far - variables, arrays, records - lives in memory, and memory is cleared the moment the program ends: the shop's day of sales vanishes with the closing statement. A file stores data in secondary storage, where it is kept after the program ends, with the power off, and can be read again tomorrow by the same program or a different one. That permanence is the first need; the second is sharing, because a file on storage is what one program writes and another reads - the day's orders written by the till and read by the bookkeeper's program - and what travels as an attachment across a network. Both needs are one idea: the file is data that outlives the program, so programs that end or never meet can still exchange it.

### Handling text files in pseudocode

A text file is handled in four moves, in a fixed order. Open it: OPENFILE with the file name and a mode. READ reads lines from the start of the file. WRITE creates the file afresh, so anything already in it is lost. APPEND adds new lines to the end of an existing file and keeps what is there. Read or write lines: READFILE <file>, <string> reads the next line into the string, and WRITEFILE <file>, <string> writes the line. Test the end: EOF(<file>) returns TRUE when there are no more lines to read, so a loop that reads a whole file tests NOT EOF(<file>) before each READFILE. Close it: CLOSEFILE with the same file name. One quotation-mark rule runs through all of it: a literal file name is a string, so OPENFILE "Orders.txt" FOR READ has quotation marks, whereas an identifier holding a file name has none, so OPENFILE FileName FOR READ opens the file whose name the identifier holds - and quoting the identifier would look for a file actually called FileName. And one geometry rule: a text file is read line by line from the start, so reaching line 10 means reading lines 1 to 9 first; there is no jump to a line.

### Worked example: one day of orders

A kiosk writes the day's orders to "Orders.txt" and the next morning's program totals them. Writing, with APPEND because yesterday's orders are already there:

```pseudocode
DECLARE Order : STRING
DECLARE Order : STRING
FOR Count <- 1 TO NumberOfOrders
   INPUT Order
   WRITEFILE "Orders.txt", Order
NEXT Count
```

Reading the whole file, with the EOF test guarding each read:

```pseudocode
DECLARE Line : STRING
DECLARE TotalOrders : INTEGER
TotalOrders <- 0
OPENFILE "Orders.txt" FOR READ
WHILE NOT EOF("Orders.txt")
   READFILE "Orders.txt", Line
   TotalOrders <- TotalOrders + 1
ENDWHILE
CLOSEFILE "Orders.txt"
```

The reading loop shows the two tests C-16's structure names: the WHILE tests NOT EOF before each READFILE, so the loop never reads past the last line, and the body reads one line and counts it, so the count grows exactly with the lines read. Close the file with the same name it was opened with, or the next open may find it still locked - the discipline is open, work, close, always in that order, and the same name in all three places.

### Common errors

Three slips recur. Quotation marks on the wrong side: the literal name "Log.txt" takes them, the identifier LogFile does not - the test is whether it is the name itself or a variable holding the name. The wrong mode for keeping data: WRITE starts the file again, so old lines are lost, whereas APPEND keeps them and adds to the end - the test is whether the old contents should survive. And misusing the file's shape: a text file is read from the start, line by line, so reaching line 10 means reading 1 to 9 first, and EOF(<file>) carries the file's name - the test is whether the jump skips lines, because a text file offers no jump.
