## From files to a relational database

### The limitations of the file-based approach

In a file-based approach, each application keeps its own files: the billing system its billing files, the appointment system its appointment files, no shared store between them. Two limitations follow, and they compound. Data duplication: data one application needs that another already holds is entered again into a second file, so the customer's address lives in the billing file and again in the delivery file - storage is wasted, and worse, the copies drift: the address changed in one file leaves the other stale, and the same customer has different addresses in different systems. Program-data dependency: each program is written to its files' layouts - where each field starts, what each record ends with - so a change to a file's structure forces changes to every program that uses it, which is why file-based systems resist change: the structure cannot move without the programs moving with it. The words to keep straight: dependency runs from the programs to the data's structure, not from the data to the programs, because it is the programs that break when the files change.

### How a relational database addresses them

A relational database stores data in tables that every application shares, and it answers each limitation at its source. Duplication: each value is held once, in one table, so there are no copies to disagree - the address is in the patient table, and billing and delivery both read it there, so an update is made in one place and every application sees the new value. Program-data dependency: the DBMS (the database management system, 8.2's subject) sits between the programs and the data, so a program asks for data by table and attribute name - 'the patient's address' - not by position in a file layout, and the DBMS finds it. A change to how data is stored is absorbed behind the DBMS, so the programs that ask by name are untouched, and it is the DBMS that depends on the layout now, not every program. The two answers generalise: centralise the data, and interpose a manager - which is the database's whole architecture in two moves.

### The terminology of the relational model

The relational model has its own words, and they travel in pairs. An entity is what a table stores data about - the patient, the product, the order - and a table holds one entity's data. A record in the table (also called a tuple) is one row: one patient, one order. An attribute (also called a field) is one column: the patient's telephone number, the order's date. Keys come next. A primary key is the attribute, or attributes together, whose value identifies each record uniquely - PatientNo - and a candidate key is any attribute that could do the job, one of which is chosen. A secondary key is an attribute used to search a table that does not identify a record uniquely: Surname narrows a patient search to a group, and many records may share it. A foreign key is an attribute in one table that is the primary key of another table, and it links the two - the appointment's PatientNo points at the patient's row. Relationships come as one-to-one, one-to-many (the commonest) and many-to-many, which is implemented as two one-to-many relationships through a link table. Two rules complete the core. Referential integrity: a foreign key's value must match a primary key value in the referenced table, so a record cannot point at a record that does not exist. And indexing: the DBMS keeps an index over a table's search attribute, so records are found through the index instead of by reading the whole table.

### Worked example: one pharmacy, two architectures

A pharmacy in Otjiwarongo keeps billing in one system and stock in another, both file-based. A supplier moves house. The billing file's supplier address is updated; the stock file's copy is not; the next stock order goes to the old address - duplication, and the disagreement it grows. A new attribute is added to the supplier record, a credit rating: every program that reads the supplier files must be changed and retested - program-data dependency, and the six-month change-over it forces. Now the same pharmacy on a relational database. SUPPLIER(SupplierNo, Name, Address, Phone, CreditRating) is one table, read by every part of the system; the address is updated once, and both the billing screens and the stock orders see it, because there are no second copies. The credit rating is a new attribute of the supplier table, added by the DBA behind the DBMS: no program asks the DBMS differently, because programs ask by name, and a program that wants the rating simply asks for it - the change ripples into no program that does not need it. Every limitation of the first architecture is answered by a feature of the second, which is the point of the pair.

### E-R diagrams

An entity-relationship diagram documents a database design before the tables are built: a box for each entity, and a labelled line between two entities for each relationship, with the relationship's kind marked on the line. A dental practice's design, drawn in words. Three entity boxes: PATIENT, APPOINTMENT, DENTIST. One line from PATIENT to APPOINTMENT, labelled with the relationship and marked one-to-many: one patient, many appointments, the 'many' at the appointment end. One line from DENTIST to APPOINTMENT, labelled and marked one-to-many: one dentist, many appointments. When a many-to-many appears - a medicine appears on many prescriptions and a prescription holds many medicines - the line is marked many-to-many in both directions, and the design resolves it with a link entity: PRESCRIPTION_MEDICINE between PRESCRIPTION and MEDICINE, holding the keys of both, so the one many-to-many becomes two one-to-many relationships. Reading the diagram answers design questions at a glance: which entities exist, how they are linked, and where the foreign keys will sit - on the many side of each one-to-many line, which is where the linking attribute is always stored. The diagram comes before the tables because checking a line is cheaper than rebuilding a table. Drawing one in an answer is naming the three things a reader of the design will look for: the boxes, the lines and the marks - a box per entity, a labelled line per relationship, and the one-to-one, one-to-many or many-to-many kind marked at each end - so a described diagram is complete when a reader could build the tables from it unaided.

### Common errors

Three slips recur here. Treating a database and a table as one thing: a database is made up of tables, and a tuple is one row of one table - the test is whether the database can contain several of it, which it can for a table and cannot for the database itself. Giving primary keys where foreign keys were asked for: a primary key identifies records in its own table, whereas a foreign key points at another table - the test is whether it points at another table. And reversing program-data dependency: the programs depend on the structure of the data, and the test is to name what depends on what - the programs break when the files change, not the reverse.

## Normalisation

### The three normal forms

Normalisation reorganises a table until every attribute depends on the key, the whole key and nothing but the key, and the forms are the stages of that journey. First Normal Form: no repeating groups - each field holds a single value, and a primary key identifies each record. A patient list with a column of that patient's appointments repeated in one row is not 1NF; flattened to one row per appointment, it is. Second Normal Form: 1NF, plus no non-key attribute depending on only part of a composite primary key. In the flattened appointment table keyed by (PatientNo, Date, Time), PatientName depends on PatientNo alone - part of the key - so the table is 1NF but not 2NF until PatientName moves to its own patient table. Third Normal Form: 2NF, plus no non-key attribute depending on another non-key attribute. DentistName depends on DentistNo, and both are non-key in the appointment table, so the table is not 3NF until the dentist's data moves to its own table. Note the shape of the journey: each form removes one kind of dependency, and each removal moves attributes into the table of the thing they truly depend on.

### Testing whether a table is in 3NF

Testing runs the definitions in order, and the first failure names the form the table is stuck at. Check for repeating groups: any attribute holding several values in one record breaks 1NF - stop, the table is unnormalised. Check for part-key dependencies: with a composite key, take each non-key attribute and ask which part of the key fixes its value - if any part alone fixes it, the table is 1NF and no further. Check for non-key dependencies: take each non-key attribute and ask what fixes its value - if the answer is another non-key attribute, the table is 2NF but not 3NF. A single-attribute key skips the middle test, because it has no parts, so a 1NF table with a single-attribute key is 2NF as well, and only the non-key test remains. A worked mini-example for each failure keeps the three straight: a row holding several appointment values in one field is a 1NF failure; a patient’s name keyed to only part of (PatientNo, Date, Time) is a 2NF failure; a dentist’s name keyed to a dentist’s number, both non-key, is a 3NF failure - and each failure’s remedy is the same move: the fact goes to the table of the thing it depends on. One habit serves every test: read the table’s rows aloud and ask, for each attribute, what fixes this value - the answer names the dependency, and the dependency names the form.

### Worked example: normalising an appointment list

Start unnormalised, one row per patient with the appointments repeated: (PatientNo, PatientName, PatientTel, and for each appointment Date, Time, DentistNo, DentistName, Treatment). To 1NF: flatten - one row per appointment, key (PatientNo, Date, Time), fields PatientName, PatientTel, DentistNo, DentistName, Treatment. Each field now holds one value. To 2NF: find the part-key dependencies. PatientName and PatientTel depend on PatientNo alone, so they move out: PATIENT(PatientNo, PatientName, PatientTel), and the appointment table keeps PatientNo, which links back. To 3NF: find the non-key dependency. DentistName depends on DentistNo, a non-key attribute in the appointment table, so it moves out: DENTIST(DentistNo, DentistName), and the appointment table keeps DentistNo. The final design, three tables: PATIENT(PatientNo, PatientName, PatientTel); DENTIST(DentistNo, DentistName); APPOINTMENT(PatientNo, Date, Time, DentistNo, Treatment), with PatientNo and DentistNo foreign keys to the tables they name. Every attribute now depends on its table's key, the whole key and nothing but the key - and the anomalies are gone: a dentist's name is stored once, a patient's move is one update, and deleting the last appointment deletes no dentist.

### Producing a normalised design

Producing a design from a description runs the same moves forward. Identify the entities - the things the description counts: farmers, plots, crops - and give each a table with a primary key. Move each repeating group into its own table: the crops repeated in a plot's row become a CROP table with the plot's key as a foreign key back. Move each attribute that depends on something other than its table's key into the table of the thing it depends on: the farmer's name depends on the farmer, not the plot, so it lives in FARMER. Resolve any many-to-many with a link table holding both sides' keys. The result is the same journey as testing, run in the building direction: no repeating groups, no part-key dependencies, no non-key dependencies - three tables where one grew, and every fact stored exactly once.
