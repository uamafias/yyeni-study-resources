## Images: bitmaps, file sizes and vector graphics

### How a bitmapped image is stored

A bitmapped image is divided into a grid of pixels, and the file stores one binary colour code for the colour of each pixel, row by row. For a black-and-white line image one bit per pixel is enough, a 0 for white and a 1 for black; a colour photo needs many more bits per pixel so that each can name its own colour. The pixel data on its own is unusable: software needs to be told the grid's size and how many bits each pixel takes. That is the file header's job. A bitmap header carries the data needed to read the image, such as the image resolution, the colour depth, the file size and where the pixel data starts, so any software that knows the format can reconstruct the picture without being told anything else. The codes themselves say nothing about meaning: the same pattern read with a different colour depth would show as different colours.

### Image resolution, screen resolution and colour depth

Image resolution is the number of pixels in the stored image, given as width by height: a 1200 x 800 image holds 1,200 pixels along each of 800 rows. Screen resolution is a different thing: the number of pixels the display itself can show, such as 1920 x 1080. The image's resolution is stored in the file; the screen's is a property of the monitor, and opening the same file on a different screen changes neither the file nor its pixels. The two meet in one place: when a 1200 x 800 image is shown full-screen on a 1920 x 1080 display, the software stretches the stored pixels to fill the screen, so the picture appears larger but its pixel count has not grown by one. Colour depth, also called bit depth, is the number of bits stored for the colour of each pixel. Raise it and more colour codes become available, because the count of codes is two to the power of the depth: 8 bits give 256 colours, 16 bits give 65,536, and 24 bits give more than 16 million.

### Estimating a bitmap's file size

The pixel data size follows from two numbers: how many pixels there are, and how many bits each one takes. The estimate is the number of pixels multiplied by the colour depth in bits per pixel, plus the small header, which is usually left out of the estimate. Three steps finish it: count the pixels (width x height); multiply by the colour depth to get bits; divide by 8 to get bytes. A prefix is applied to the bytes, never to the bits, which is where the 1.1 prefixes return. For example, a 640 x 480 image at 16 bits per pixel holds 307,200 pixels, so its pixel data is 307,200 x 16 = 4,915,200 bits, which is 614,400 bytes, about 614 KB.

### Worked example: one photo, three estimates

A wildlife photographer's shot is stored as a 1600 x 1200 bitmap. At 8-bit colour, the pixel count is 1600 x 1200 = 1,920,000, the pixel data is 1,920,000 x 8 = 15,360,000 bits, and in bytes that is 15,360,000 / 8 = 1,920,000 bytes. At 16-bit colour the same shot doubles to 3,840,000 bytes; at 24-bit colour it becomes 5,760,000 bytes, which is 5.76 MB at a million bytes per megabyte. The colour depth changes nothing about the grid: the same 1,920,000 pixels each store more bits. If instead the photographer doubles the resolution to 3200 x 2400, the pixel count quadruples to 7,680,000, because both the width and the height doubled, so the 8-bit version grows to 7,680,000 bytes. Doubling one dimension doubles the pixels; doubling both quadruples them.

### What changes, and what it costs

Changing the elements of a bitmap moves quality and size together. Raise the colour depth: more colour codes become available, so tones come closer to the original, and each pixel takes more bits, so the file grows in step, with double the depth costing double the data. Raise the image resolution: more pixels describe the same scene, so the picture stays sharp at larger display and print sizes, and the file grows with the pixel count. Change the screen resolution: nothing in the file changes at all, because the file stores the image's own pixels and the screen merely decides how large they appear. That distinction answers a question that costs marks when blurred: a file does not get bigger by being opened on a better monitor, because the monitor is not part of the file. Watch the direction of each change as well. Halving the colour depth halves the pixel data but throws away colour codes the picture may have needed, so a photo of a sunset comes out banded where it was smooth. Halving the image resolution halves the pixel count but the picture loses its fine edges, so text in the image frays. One change leaves both alone: moving the file to another computer keeps every pixel and every bit of depth, because the file carries its own description wherever it goes.

### How a vector graphic is stored

A vector graphic takes the opposite approach: instead of storing how the picture looks, it stores how to draw it. The file holds a drawing list, and the list's entries are drawing objects, one per shape in the picture. Each drawing object is a command with its properties: for a circle, the centre's coordinates, the radius, the line thickness and colour, and the fill colour if the shape is filled. To display the image, the software reads the list and executes each command in turn, using its properties, and the picture is produced at the end. Because the file states what to draw rather than what each pixel looks like, the picture can be drawn at any size: the properties are numbers, and the software scales them as it draws. One caution about the term: the drawing list is the set of objects that make up this image, not a library of every shape the software could ever draw.

### Worked example: a badge from its drawing list

A cycling club's badge is one circle inside one square, and its drawing list holds two objects. RECTANGLE, with properties left corner (40, 40), width 120, height 120, line black, fill none. CIRCLE, with properties centre (100, 100), radius 45, line none, fill black. Drawn in list order, the square appears first and the circle lands inside it, centred on the square's own centre. When the club wants the circle twice as wide, one object changes: the CIRCLE's radius property from 45 to 90, and the RECTANGLE is untouched. That is the everyday power of the form: an edit touches the one object named, and the redraw produces the badge again at whatever size is asked. Had the badge been a bitmap, enlarging the circle would mean regenerating pixels, and a large print would show the limits of the grid.

### Choosing between bitmap and vector

Which representation suits a task follows from what the image is. A photograph is continuous and irregular, with tones shifting across every region of the scene, and a bitmap stores a colour code for each pixel, so it matches the subject: each pixel holds its own colour, which is why photographs are stored as bitmaps. A logo, a diagram or a line drawing is made of a few clean shapes, and a vector graphic stores exactly those, as objects with properties, so the file stays small and the picture redraws at any size, sharp on a business card and on a billboard. The costs sit on both sides. A bitmap's grid is fixed: enlarge it far past its resolution and each pixel covers more space, so the picture goes blocky, and the file carries a code for every pixel however plain the picture. A vector file cannot sensibly describe each pixel of a photo, so it is the wrong tool for one. When a page needs both, both forms are used, each for the job it does: a wildlife poster might keep the animal shot as a bitmap and the reserve's boundary map as a vector, because the poster needs the photo's tones and the map's clean lines at every size.

### Common errors with images

The recurring slips, and the tests that catch them. Taking colour depth for image resolution: resolution counts pixels, width by height, while colour depth counts bits per pixel; the test is to add colours and keep the pixels the same, because what then changed is the colour depth. Believing a different monitor changes the file: the file stores the image resolution, and the screen's own resolution is a property of the display, so opening the file elsewhere changes how large the picture appears, not what is in it. Reading the drawing list as a library of shapes: the list holds the objects of this image only, so it redraws this image and nothing else. Leaving a file size in bits: colour depth is in bits, and bytes come from dividing by 8 before any prefix is applied.

## Sound: sampling and its settings

### How sound is represented

Sound is analogue: the air pressure rises and falls in a continuous wave, taking any value in between. A computer's memory cannot hold a continuum, so sound is stored by sampling it. A microphone turns the pressure into a continuously varying voltage; an analogue-to-digital converter measures the wave's amplitude at regular intervals, and each measurement is stored as a binary value. The recording is then a sequence of samples, each one a binary number. Two settings shape the result. The sampling rate is the number of samples taken per second, measured in hertz, and it says how often the wave is measured. The sampling resolution is the number of bits stored per sample, and it says how precisely each measurement is kept: more bits distinguish more amplitude levels, so the stored value sits closer to the wave's true height at that moment. Together they set what the recording can hold: a rate of 8,000 samples per second with 8 bits per sample keeps 8,000 measurements a second, each one of 256 possible levels, and the recording's character is fixed at the moment those settings are chosen.

### Worked example: a voice recording's size

A community station records a 10-second voice track at 8,000 samples per second with a sampling resolution of 8 bits. Samples taken: 8,000 x 10 = 80,000. Bits stored: 80,000 x 8 = 640,000. Bytes: 640,000 / 8 = 80,000, so the recording is 80,000 bytes, about 80 KB. Re-recorded at 16,000 samples per second with 16 bits per sample, the same ten seconds take twice the samples, each twice as wide: 16,000 x 10 = 160,000 samples, at 16 bits each, which is 2,560,000 bits and 320,000 bytes, four times the data. Doubling one setting doubles the data; doubling both settings at once multiplies it by four.

### What changing the sampling does

The two settings can be raised, and each purchase is paid for in file size. Raise the sampling rate, and the wave is measured more often, so more of its rises and falls are captured and the rebuilt sound is truer; the file grows because each second contributes more samples. Raise the sampling resolution, and each measurement is kept more precisely, so quiet passages and loud ones alike are recorded closer to the wave's true amplitude; the file grows because each sample takes more bits. Halve either, and the size halves in step. Neither setting can be recovered later: a recording made at 8,000 samples per second stays that coarse however finely it is played back, because the missing measurements were never taken. With too low a rate, movement between samples is lost, and the replay can differ from what was played. With too low a resolution, the wave's height is rounded to the nearest of the few levels available, so the rebuilt wave steps instead of sweeping, and the sound that comes back is a rough copy of what went in.

### Common errors with sound

The recurring confusion is between the two sound terms and the picture term. Sampling rate is how often, measured in hertz; sampling resolution is how precisely, measured in bits per sample; image resolution counts pixels in a picture, a different thing with a near-identical name. The test: whatever is quoted in hertz is a count per second, and whatever is quoted in bits is a width, so hertz does not measure a resolution and bits do not measure a rate.
