## Design tools: structure charts and state-transition diagrams

### Structure charts

A structure chart draws a program's decomposition. Each box is a module - one sub-task, one named job. The lines join the boxes in the calling order: the calling module above, the modules it calls below it, so the chart is read top-down. On those lines the parameters are drawn as circles: a hollow circle carries data - a value the called module works on - and a filled circle carries a flag - a Boolean signal, such as a completion or error indication. A BYREF parameter is shown as data going both ways on the same line, because the value travels down into the module and the changed value travels back up. A worked chart in words, a lodge check-in: the top box HandleCheckIn calls three boxes beneath it. FindRoom takes one hollow circle down (the guest's name) and returns one hollow circle up (the room number). RecordBooking takes two hollow circles down (the guest's name and the room number) and returns one filled circle up (the recorded flag). IssueKey takes one hollow circle down (the room number). Read as a design, the chart says the check-in has three sub-tasks, each takes what it needs, and the flag tells the caller the booking was recorded - a reader can check all of that against the problem before any code is written, which is the chart's whole purpose.

### Deriving pseudocode from a structure chart

The chart is the design, and the code is derived from it box by box. Each box becomes a module: the top box becomes the main program or top procedure, and each box beneath it becomes a module with that job. Each line beneath a box becomes a call with the line's circles as its parameters: the down-circles are the arguments passed in, and the up-circles are the results - a function's returned value, a BYREF parameter, or a flag the module sets. The lodge chart derives into FUNCTION FindRoom(GuestName : STRING) RETURNS INTEGER, a PROCEDURE RecordBooking with the two data parameters and the flag, and PROCEDURE IssueKey(RoomNumber : INTEGER), with the top module calling each in the chart's order. The derivation runs the other way too: a program's modules and parameters can be drawn as a chart, and the drawing is the check - a module whose box needs five circles is a module doing more than one job, and a line with no circles is a call that passes nothing, which is worth a second look at the design stage.

### State-transition diagrams

Some algorithms are better documented as situations than as steps. A state-transition diagram shows an algorithm as states and transitions: each state is one situation the system can be in, and each transition is the event that moves the system from one state to the next, drawn as a line from the old state to the new one labelled with the event. A gate controller in words: two states, Locked and Unlocked; a transition 'coin' from Locked to Unlocked, and a transition 'push' from Unlocked to Locked. The diagram's purpose is to document behaviour that depends on history: what the gate does when pushed depends on which state it is in - a Locked gate swallows the push, an Unlocked gate opens - and the diagram puts every state against every event in one picture, so the reader can check the behaviour for gaps. The structure chart suits behaviour that is a decomposition into jobs; the state diagram suits behaviour that is a set of situations and events - and the two design tools sit together, one for what the program is made of, one for how it behaves.

### Common errors

The recurring slip in structure charts is the wrong circle. A hollow circle carries data and a filled circle carries a flag - a Boolean signal, not a value - so the test is whether the parameter is a flag: if it is, fill the circle. And a BYREF parameter is data going both ways on the one line, because the value returns changed - a single one-way arrow on a BYREF line loses the way back.
