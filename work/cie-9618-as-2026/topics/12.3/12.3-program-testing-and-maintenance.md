## Errors: exposing, locating, correcting

### Exposing faults: dry runs and walkthroughs

A fault is a mistake in the program, and the first tools for exposing one are used at the desk, before any run. A dry run traces the code by hand: the tester takes a sheet, a set of variable columns, and the program, and executes it statement by statement on paper, recording each variable's new value in a trace table after each statement. A walkthrough is the same trace done in company: the author leads others through the code, the questions come from fresh eyes, and the author explains what each statement is supposed to do - which is when a statement that does something else is heard for the first time. What the trace table buys is honesty: the table records what the program actually does, not what the author meant, so a logic error is found by comparing the traced values with the values the problem required. And the three error types are told apart by a three-question test. Did it translate? No - a syntax error, a break in the language's rules, caught at translation with a rule named. Did it run? No - a run-time error, the program stopping mid-run on an operation it cannot complete: reading a file that does not exist, dividing by zero, reading past an array's upper bound. Did it give the right answer? No - a logic error, the program running happily and delivering the wrong result: a total that misses the last item, a condition that tests the wrong variable. The worst of the three is the logic error, exactly because it runs - the program looks healthy and quietly misleads, which is why the trace table, which records what actually happened, is the tool for it. A worked miniature sets the whole method in motion. The till program’s trace begins Total 0, and the first sale of 60 takes the row Total 0, Sale 60, after the statement Total 180 - and the required value at that point is 120, so the row is the first departure and the loop’s bound is the suspect; changing the bound and re-tracing gives the right total, and the second trace’s matching rows are the correction’s evidence. Every logic-error question in this topic is that miniature wearing different clothes, and the method never changes: trace, find the first departing row, change that statement, re-trace, and show the rows now matching.

### Correcting identified errors

Correction begins where identification ended: at the statement that produced the traced wrong value. The discipline is to change that statement and only that statement, because the trace established where the program's behaviour first departed from the required - a change one statement early or late fixes a symptom and leaves the cause, and a change somewhere the trace did not look adds a second fault to the first. Three worked corrections show the discipline. A total that misses the last item traces to a loop whose end is one short: the trace table's last row shows the loop finishing before the last element, so the correction moves the loop's bound by one. A condition that tests the wrong variable traces to a selection whose test uses a variable that was never set for this purpose: the row before the selection shows the intended variable sitting ready and unused, so the correction changes the condition, not the computation. A run-time failure past an array's end traces to an index that grew beyond the upper bound: the trace shows the index's growth past the declared limit, so the correction is the guard that stops the access or the loop that ends at the bound. After any correction, the test that exposed the error runs again, and so does the whole program - because a correction is a change, and a change can break something else, which is what the next block's test strategy is for.

### The testing methods

The methods of testing form a series, each answering a different question. Before the code runs: the dry run and the walkthrough, at the desk. With the code's structure known - white-box testing: the tester reads the code and chooses test data to exercise it - every path through a selection, the loop run once and not at all - so the data is drawn from the code, and the test asks 'does this code do what its structure allows?'. With the code unseen - black-box testing: the tester uses only the specification, choosing data from the requirements and checking outputs against them, so the test asks 'does this program meet its requirements?' - and never looks inside. As the modules meet: integration testing, which checks that separately tested modules work together, because modules that each pass alone can still fail together at their interfaces - the caller's arguments in the wrong order, the flag never set. Before the real modules exist: stubs, simple stand-in modules with the interface but a fixed return, so the calling module can be tested while the called ones are still being written. As the system nears its users: alpha testing, in-house, the development team's own users running the whole system; beta testing, the system released to selected real users outside the team, whose findings arrive from real use; and acceptance testing, the customer checking the delivered system against the requirements and accepting or rejecting it. The series runs from the desk to the customer, each method asking a question the earlier one could not. A note on scale keeps the series honest: each method exists because the one before it leaves a question open, and the whole series is a program’s defence in depth - the walkthrough catches what one reader misses, the white-box round exercises the paths the structure allows, the black-box round checks the requirements from outside, the integration round joins what passed alone, the stubs let the joining be tested early, and the alpha, beta and acceptance rounds move the checking closer and closer to the user who will live with the result. No single round certifies a program; the series does, which is why a test plan lists rounds of more than one kind.

### Common errors

The recurring slip is mixing the three error types. A syntax error breaks the rules of the language and is found at translation; a logic error runs but gives the wrong result; a run-time error stops the program while it runs. The test asks three questions in order: did it translate? did it run? did it give the right answer? And the testing slip: integration testing checks that separately tested modules work together - the test is on modules combined, not on one module, because single-module tests were done before.

## Test strategy and plan, test data, maintenance, amendments

### Test strategy and test plan

Testing at scale is managed in two documents. The test strategy states what will be tested and how: which methods the project will use - black-box against the specification, white-box on the modules that compute money, integration at the interfaces, acceptance with the customer - and what the testing must achieve before the program is released. The test plan is the strategy written down as work: a concrete schedule listing the tests, one by one, each with the data it will use, the expected result from the specification, and a column for the actual result - so a test plan is a document a tester can work through and check off, and the expected-against-actual columns are what turn testing into evidence. The two differ in altitude, not in kind: the strategy says 'money computations are tested white-box and the interfaces are tested by integration', the plan says 'test M7: SaleTotal with prices 0 and 0.01, expected ...', and the plan's each-test-a-row shape is why the plan is the document an auditor reads. Both exist because unmanaged testing finds whatever it happens to find - the strategy and the plan are what make the finding deliberate.

### Choosing test data

Test data is chosen by kind, and the kinds are the specification's categories. Normal data is valid data in the ordinary range - a booking for 2 nights, an age of 30 - because the program must first be shown to work where it will live. Abnormal data is invalid data the program should reject - a negative age, thirteen nights where the maximum is twelve - because a program's behaviour on the invalid is a behaviour worth testing: the rejection is required, so the test checks the program refuses. Extreme data is valid data at the limits of the acceptable range - twelve nights where twelve is the maximum - because the last valid value is where a careless bound goes wrong. Boundary data tests either side of a limit - eleven, twelve, thirteen - because errors sit at the edges of ranges: a loop that ends one early works for the middle of the range and fails only at the top, so a boundary pair is the data that catches it. The choice among kinds follows the test's purpose: to show working, choose normal; to show rejecting, choose abnormal; to show the range is exactly right, choose extreme and boundary - and a plan whose data is all middle-of-range has tested only the easy half of the specification.

### Continuing maintenance and its three forms

Delivery is not the end, and continuing maintenance is the stage that owns the rest of the program's life. The need comes from three directions, and they name the three forms. Errors surface in use, in combinations the testing never met - a leap year, a customer with two middle names - and fixing them is corrective maintenance. The environment around a program changes - the levy rate changes in law, the operating system is replaced, the bank's account format grows a digit - and adjusting the working program to the changed world is adaptive maintenance. The users, working with a program that meets every requirement, see how it could serve them better - the monthly summary, the one-keystroke repeat - and improving the working program is perfective maintenance. The three are told apart by one question: is something broken, has something changed around it, or is it merely improvable? That question is the whole discrimination, because the forms share no situations - a fault is corrected, a change is adapted to, an improvement is perfected. And the need for maintenance does not close, because the world does not stop changing around a working program: the program left unchanged while the world around it moves is the program quietly becoming unusable, which is why the maintenance stage continues as long as the program is in use.

### Amending a program to enhance functionality

Amending an existing program is a skill of its own, because the program is not yours and its behaviour is not what you think it is. Four moves. Read with a trace first: run a dry run or a walkthrough on the existing code, recording the variables' values, until you can say what each module does and where each value is set - the amendment is placed in what the program does, never in what you assumed it does. Place the change at the owner: find the statement that owns the affected value - the total the new fee must join, the record the new field extends - and place the amendment there, because a value has one owner and the change belongs with it. Follow the existing style: the new statements use the identifiers, the modules and the naming of the code they join, so the program reads as one program after the change - and where the new functionality is more than a statement or two, it goes in a new module called where the change was needed. Re-test the whole program: the new functionality is tested with new data, and the old program is re-tested with the old test plan, because a change to one value travels to every use of it - the amendment that 'only adds a line' has broken more programs than the bug it fixed. The discipline in one line: read before you write, place the change at the owner, follow the style, and re-run everything. A worked miniature of the whole move: a delivered program totals a stall’s takings, and the stall now sells gift vouchers that should join the takings. The amendment reads the existing loop with a trace until the total’s owner is named - the loop that adds each sale - places the voucher’s addition inside that loop with the sale’s own identifier style, writes nothing new outside it, and re-tests with the old plan’s rows plus new rows for vouchers. The change is one statement inside the owner’s loop, the program reads as one program, and the re-run certifies both the old behaviour and the new - which is what amending means: the program grows without becoming a stranger.

### Common errors

Two slips recur. Boundary data confused with abnormal data, or a range given where a value was asked for: boundary data tests either side of a limit with valid values - eleven, twelve, thirteen - whereas abnormal data is invalid data the program should reject. The test asks two questions: should the program accept it? Is it on the edge? And the maintenance forms named for the wrong situation: corrective fixes errors, adaptive responds to a change around the program, perfective improves a working program - the test asks: is something broken, has something changed around it, or is it merely improvable?
