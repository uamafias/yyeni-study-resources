## The program development life cycle

### Why a life cycle is needed

A program development life cycle is a managed sequence of stages - analysis, design, coding, testing and maintenance - and the need for it is the need for management. A program written without stages leaves each activity undone in the rush to the next: requirements never analysed show up later as a design that solves the wrong problem; a design never drawn shows up as code whose pieces do not fit; code never tested shows up in use, where every fault costs a user's evening; a program never maintained dies with its first needed change, because nobody knows where to change it. The cycle names each activity as a stage, gives each stage an output the next stage can work from, and makes each stage's completion visible before the next begins, so the program's progress is checked stage by stage - which is what management means here: the work is sequenced, and its state is known. The cycle also buys control: each stage has an owner, an output and an end, so the program's progress is reported in the currency managers can read - which stage, which output, what done means - and a late stage is visible as a late stage, not as a feeling that the program is taking long. That is the quiet second purpose of every cycle shape in the next section: whatever arrangement of stages a cycle chooses, it keeps the work legible to the people paying for it.

### Different cycles for different programs

Not every program deserves the same cycle, and the decider is the requirements. Where the requirements are fixed and knowable in advance - a payroll whose rules are set by statute and change once a year, a controller for a device whose behaviour is specified - the waterfall suits: the stages run once, each after the previous and each completed before the next begins, so the whole requirement is settled at the start and the program is delivered complete. Where the requirements are expected to change or to be discovered - a booking system whose users refine what they want as they see what they get - the waterfall's one pass is a trap, and the iterative cycle suits instead: the stages run in small repeated passes, each pass delivering a working part of the program, so the users' discoveries from one pass feed the next. Rapid application development compresses the cycle for urgent work: intensive user involvement throughout, a working prototype built quickly and reworked, and development tools that speed the building - trading long analysis for a fast first version that is allowed to be wrong about details. The comparison is the answer to the question 'why different cycles?' - and the comparison is what the answer must contain, because saying only that a cycle is useful answers a different question.

### Benefits and drawbacks of each cycle

Each cycle's benefit is the other's drawback, which is why the choice is a trade. The waterfall's benefit is its completeness: every requirement settled before design, every design before code, so the delivered program is documented, and the large fixed problem is solved in one coherent effort. Its drawback is the same coin seen from the other side: nothing works until late, so a wrong requirement discovered at testing has travelled through design and code already - a late fault in a waterfall is expensive. The iterative cycle's benefit is its working program early: users hold a part of the system in the first pass, so wrong requirements are discovered while they are cheap to fix, and change is the cycle's normal business. Its drawback is the mirror: the parts are integrated gradually, so the whole system's shape can drift, and a pass-by-pass development needs the discipline to revisit earlier work - documentation and time can be lost to the rhythm of passes. RAD's benefit is speed with the user in the room: the prototype is real, the feedback immediate. Its drawback is commitment: a project run this way demands the users' time for its whole length and a team and tools that can keep the pace, and the prototype-first habit can leave a program that works but is built on quick foundations that were never re-laid. A justified choice names the program's requirements, the users' availability and the deadline, and takes the cycle whose costs the situation can pay.

### The stages: analysis, design, coding, testing, maintenance

The program's stages, in the order the waterfall shows them plainly. Analysis: state what the program must do. The problem's owners are interviewed, the current system is studied, and the requirements are written down as statements the program can be checked against - the output is the requirements document. Design: state how the program will do it. The data is designed first - the records and arrays of topics 10 and 11 - then the modules, their names, parameters and interfaces, and the algorithms each will run; the outputs are the designs that coding follows. Coding: write the program in a language, module by module against the design, with the identifiers named for their data. Testing: check the program against the requirements - the dry runs and test data of 12.3, from single modules to the whole system. Maintenance: keep the program working after delivery, and it takes its three named forms because programs are changed for three different reasons - corrective maintenance fixes faults the testing missed; adaptive maintenance adjusts the program to a changed environment, a new levy rate or a new operating system; perfective maintenance improves the program in response to new requirements from its users. Each stage's output is the next stage's input, which is why the stages are a cycle and not a list: the requirements drive the design, the design the code, the code the testing, and the documented program is what maintenance can change safely - and what analysis' output drives next time around.

### Common errors

The recurring slip is answering the wrong question with a true sentence. Asked why different life cycles exist, a learner explains why a life cycle is useful - the stages, the checking, the management. The question was comparison, and the answer must compare: fixed requirements suit the waterfall, changing requirements suit the iterative cycle, urgent work with committed users suits RAD. The test: does the answer compare cycles? It must.
