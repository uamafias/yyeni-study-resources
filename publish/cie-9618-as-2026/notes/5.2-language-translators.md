## Language translators and the IDE

### Why translators are needed

A processor executes one thing only: machine code. A program written in an assembly language or a high-level language is a text for humans, and none of it can run until it has been translated into the binary the processor obeys. Three translators divide the work. An assembler translates an assembly language program one mnemonic at a time, each assembly instruction becoming one machine instruction, because assembly already is machine instruction by machine instruction in readable form. A compiler translates a whole high-level program into machine code before any of it runs, producing a machine-code file. An interpreter translates and executes a high-level program one statement at a time, at run time, running the statement it has just translated. The source and the working style name the translator: assembly to an assembler, whole-program-ahead for a compiler, statement-by-statement-at-run-time for an interpreter. Nothing here says which is best, because none is: each is the right tool at the moment described, and a working answer to any translator question starts by placing the program in its life - being written, being distributed, being run for years - before naming the tool, because the moment, not the tool, is what the justification turns on.

### Compiler or interpreter: the choice

Each translator earns its place at a different moment in a program's life. During development, the interpreter is the tool: each edit is tested immediately with no compile step, and when a statement is wrong the interpreter stops there and reports it, so the fix happens at once - though the interpreter does not fix anything itself; it stops so the programmer can. When the program is finished and distributed, the compiler is the tool: the compiled file runs on its own, at the machine's own speed, with no interpreter present and no source given away. The drawbacks are the same coins seen from the other side. A compiled program must be recompiled for every change, however small, and a separate compilation is needed for each different type of machine, because machine code is one machine's language. An interpreted program runs slower - the translation happens during the run - and the interpreter must be present wherever the program goes, and the readable source travels with it. Justifying a choice is matching the moment: developing, distribute-and-forget, or a one-off small run. A bank's finished program on a thousand machines goes to the compiler; a learner's daily-edited project goes to the interpreter; a weather controller that must use the processor's time exactly may go further back, to assembly and the assembler, where each mnemonic is one instruction and nothing is added.

### Partly compiled, partly interpreted

Some languages split the translation in two, and the split is deliberate. The source program is compiled, but not into any machine's machine code: it is compiled into an intermediate code, a compact form that is not the source and not any one machine's binary. At run time, a matching interpreter translates and executes that intermediate code statement by statement. Each half does the work it is best at: the compile step does the whole-program work once - parsing and checking - so runs start quickly; the interpreter does the run-time work, and because the intermediate code is the same on every machine, the one interpreter written for a machine runs every program in the language on it. The benefits are the shares: a share of the compiler's speed, because the parsing is already done, and a share of the interpreter's portability, because one intermediate file runs wherever the matching interpreter exists. The cost is the arrangement itself: two steps instead of one, and an intermediate form that is neither source nor machine code. Recognising the arrangement in the wild: where a language's programs are compiled to a file that is not a program for any one machine, and that file then runs on a matching interpreter, the language is partly compiled and partly interpreted, whatever names the tools carry.

### The IDE and its features

An Integrated Development Environment brings the tools into one program: an editor to write the code, translators to build it, and debugging tools to find its faults. The coding features work as the programmer types. Context-sensitive prompts suggest what can be written at the current point, so the editor answers before it is asked; auto-completion finishes the word being typed from the available names, so names are spelled right the first time. For initial error detection, dynamic syntax checking flags syntax errors as the code is typed, so a missing bracket or a mis-spelled keyword is caught before a run, not after. For presentation, prettyprint lays the code out consistently and expand and collapse code blocks hide and show sections, so a long program stays readable at whatever level the reader needs. The debugging tools work on the running program, and this is where the boundary lies: prompts and prettyprint help write and present code, while breakpoints, single stepping and variable watch windows help find faults in running code. A breakpoint pauses execution at a chosen statement; single stepping executes one statement at a time so the run can be followed closely; a watch window displays chosen variables' values as they change. Breakpoints and watch windows are used together: the breakpoint stops the run where the suspicion is, and the watched values show what the program believed there, which is how a fault becomes something seen. A debugging session runs in that rhythm: set the breakpoint past the last statement known to be correct, run to it, read the watched values; the first wrong value is downstream of the fault, so the breakpoint moves up and the cycle repeats until the statement that spoils the value stands alone.

### Common errors

Three slips recur here. Rolling the editing features into one: a context-sensitive prompt suggests, dynamic syntax checking checks as you type, and auto-completion finishes - the test is whether the feature suggests, checks or finishes. Naming coding tools for debugging tools: prompts and prettyprint help write and present code, while breakpoints, single stepping and watch windows help find a fault in running code - the test is whether the feature helps find a fault in running code. And giving the interpreter the fixing: an interpreter stops at an error so the programmer can fix it; it fixes nothing itself - the test is that software reports errors and people correct them.
