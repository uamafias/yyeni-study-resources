## Data types and record structures

### Choosing the data type

Pseudocode gives the types the problems use: INTEGER for a whole number, REAL for one with a fractional part, CHAR for a single character, STRING for text, BOOLEAN for a truth, DATE for a day, ARRAY for a numbered list, FILE for stored data. Choosing is not decoration: the type decides what the program can do with the value, so the choice follows the problem's use. A member number the program counts and orders is INTEGER, because arithmetic and comparison work on it - stored as STRING, the digits lose their arithmetic, because a string is not a number. A fee of 12.50 is REAL, because money carries cents and INTEGER cannot. A phone number is STRING even though it looks like a number, because what matters is the digits as written - the leading zero of 061 must survive, and no arithmetic ever runs on one. The date is the classic case: DATE is a type, and a join date held as DATE can be sorted and compared as dates, whereas '02/10/2026' held as STRING sorts by its characters, so 'first to join' answers wrongly - the string looks like a date and behaves like text, which is the whole difference a type makes.

### The record structure

A patient is one thing with details of different types - an ID that is a number, a name that is text, a birth date that is a date - and a record structure holds such a set together as one unit. The definition states the record's name and its fields, each declared with its own type:

```pseudocode
TYPE PatientRecord
   DECLARE PatientID : INTEGER
   DECLARE Surname : STRING
   DECLARE DateOfBirth : DATE
ENDTYPE
```

The form is the whole content: TYPE <name> opens the definition, every field line inside starts with DECLARE and its type, and ENDTYPE closes it - a definition missing either part is not a definition, because the reader cannot see where the record's fields end. A variable of the type is declared like any other, DECLARE Patient : PatientRecord, and a field is reached by naming the record then the field: Patient.PatientID <- 17 saves a value to the record's field, and OUTPUT Patient.Surname reads one back. What the record buys is keeping the thing together: the one value moves the whole patient - into a parameter, a file, an array of patients - whereas separate variables scatter the one thing across the program's names, and the reading and writing of a thing's data goes through its record's fields. The two worked examples that follow show both directions: a procedure that fills a record's fields from values it is given, and a function that computes a result from a record's fields - one saves into the record, the other reads out of it, and both move the whole thing as the one value the record is. A design note worth keeping: a record's fields are chosen the same way 9.2's identifiers are, by naming what each field holds, so a record's definition reads as the thing's description - ID, name, birth date - and the program's names stay honest all the way down.

### Common errors

Two slips recur. Storing a date as STRING, or giving a value in quotation marks a numeric type: quotation marks make a value a string, and a date has its own type - the test is to look for the quotation marks, then ask whether the data has its own type, and DATE exists. And writing a record definition without DECLARE on the field lines or without ENDTYPE: every field line starts with DECLARE and its type, and the block ends ENDTYPE - the test is that a definition shows both, because otherwise the fields' end cannot be seen.
