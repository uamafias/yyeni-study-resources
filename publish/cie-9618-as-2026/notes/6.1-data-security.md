## Data security, privacy and integrity, and the system around it

### Security, privacy and integrity

Three words, three different properties, and the whole topic rests on keeping them apart. Data security is protecting data from loss, corruption and unauthorised access: the file is there, unspoiled, and only the right people reach it. Data integrity is data being accurate, complete and consistent: the values are true and fit together. Data privacy is who is allowed to see particular data: personal data is limited to those with a right to see it. The properties can come apart, which is the test that keeps them apart. Data can be perfectly secure and still wrong: locked, encrypted, untouched by any outsider, with a mistyped dosage inside it, because a legitimate user made a mistake - so security does not give integrity, and integrity is protected by checking what is entered, not by stronger locks. Data can be accurate and open: a noticeboard of true figures that anyone reads, wrong for privacy though right on every value. Each property is protected by its own means - locks and access for security, checks and correction for integrity, rights and restraint for privacy - and an answer that protects one while naming another has missed the question. A question naming any of the three is first a question of which one: name the property the question asks about, name what that property is, and only then reach for the means, because the means follow the property and not the other way round.

### Why the system’s security is the data’s security

Data does not float: it lives on a machine, and the machine's health is the data's health. A failing disk corrupts the records stored on it; a power cut mid-save leaves a half-written file; protection software that is out of date welcomes the malware it no longer recognises; a network open to the internet carries strangers to the door. So data security needs the security of the computer system: the hardware kept working, the software kept current, the network filtered, the machine physically shut to strangers. A stand-alone computer is not safer by accident either: its risks come through the keyboard and the storage devices brought to it, so its measures answer those routes. The sentence to hold: the data is only as safe as the system that holds it, and every measure in this unit exists because somewhere that sentence was ignored. The stand-alone computer carries this duty too: no network connects it, so its risks arrive by keyboard and by brought-in storage device, and its measures - accounts, anti-virus scans of incoming files, updates kept current - answer those two roads, because a stand-alone machine is not an unthreatened one, only a differently threatened one.

### Measures that protect the system

The measures divide by what they check. User accounts with passwords restrict who may use the system at all, and each account's access rights decide what that user may reach - the till operator sees prices, not payrolls. Authentication techniques back the claim of identity: a password checks something the user knows; a biometric, such as a fingerprint or a face, checks something the user is, so the account opens to the person and not the knower of a word; and a digital signature checks who a message came from - the sender's software makes the signature from the message, and any receiver's software can check that the signature fits that message and names that sender, so a forged or altered message fails the check. Around the machine sit the guards: a firewall filters traffic between the computer or its network and the internet, blocking unsolicited connections from outside; anti-virus software scans files for known malware patterns and needs regular updates, because new malware appears constantly and yesterday's patterns miss today's; anti-spyware scans for and removes programs that record the user's activity and send it on. Encryption completes the set for data itself, and 6.1.2 gives it its proper home. Choosing among these measures is matching them to the routes onto the system: the keyboard is answered by accounts and biometrics, the arriving file by anti-virus and anti-spyware, the network by the firewall, the taken file by encryption - a measure aimed anywhere else guards a door the threat does not use.

### Common errors

The recurring slip is turning one property into another. Security and integrity explained the wrong way round: security protects from loss and unauthorised access, integrity is accuracy and consistency - the test is whether the data could be perfectly secure and still wrong, which it can, so they are different. And encryption given jobs it does not hold: encryption protects meaning once data is taken, not access or authorship, which 6.1.2's errors return to.

## Threats, restricting the risks, and protecting the data

### The threats

Connecting to a network connects the network to you, and four threats arrive with it. Malware is software written to harm: a virus spreads from file to file and machine to machine, damaging what it touches, and spyware sits quietly recording the user's activity - keys typed, sites visited - and sends it to whoever planted it. Hackers probe for openings: unauthorised users who gain access through weak passwords and unprotected services, reading or changing what they should never have reached. Phishing is a message that tricks the user into visiting a fake site or revealing details: the email that claims to be the bank, the link that leads to a page built to look like the bank's. Pharming does without the user's cooperation: the user is redirected to a fake site though they typed the right address, for example after the domain's address record has been altered, so the trap is on the road, not in the message. The two are told apart by the user's part in it: phishing needs a click or a reply, whereas pharming works without any action of the user's - the test is to ask what the user did. Spyware rides in on both roads - arriving hidden in downloads, arriving hidden in phishing attachments - and sits between the two camps: like a virus it arrives as software, like a keylogger it acts in silence, so it is found by anti-spyware scans and starved by the same caution that starves the phisher.

### Restricting the risks

Risks cannot all be removed, and restricting them means shrinking what each threat can reach. Access rights shrink what an intruder or an error finds: each user gets only what their work needs, so a stolen till password reaches prices, not payrolls. User training shrinks the human opening: staff told that the bank never asks for details by email, and told to take such requests to a manager, starve the phisher, because the trick works on the unprepared. Firewalls shrink the network opening: unsolicited connections from outside stop at the edge, so probes and unwanted traffic end at the wall rather than at the records. Copies beyond the one site shrink the loss: a second copy at another place means a fire, a theft or a locked-away ransom at the office loses a day at most, because the data survives beyond the building. And keeping software updated shrinks the openings that come with time: an unpatched system is a door whose lock has been published, so the updates are the shutting of it. A budget answer for any named threat is drawn from this list in two moves: name the route the threat takes, then name the measure that owns that route, because risk restriction is the pairing of the two, not a list of everything known.

### Protecting the data itself

Two methods protect the data rather than the routes to it. Encryption makes the data meaningless without the key: each file is scrambled by a method that needs its key to undo, so a stolen laptop holds scrambled bytes, a copied transmission carries scrambled bytes, and whoever took them has nothing readable. Encryption's limits are as important as its power: the data can still be intercepted - the thief still takes the file - and encryption says nothing about who sent the data, so a message can be unreadable to strangers and still come from an impostor. Proving authorship is the digital signature's job, met in the last unit. Access rights are the second method, and they work after the gate is opened: rights decide which users may read, change or delete each file or record, so the clerk reads the prices but cannot change them, and the partner's case files stay with the partners. Together the two answer the two fears: taken data that cannot be read, and authorised users who cannot reach past their work. The pairing also names each method’s blind spot: encryption without access rights leaves the authorised careless reader free, and access rights without encryption leave the taken file open, so a serious arrangement uses both, each covering the other’s gap.

### Common errors

Two slips recur. Phishing and pharming described as each other: phishing needs a click or a reply, pharming redirects without the user's action - the test is to ask whether the user acted on a message or typed the right address and was redirected anyway. And encryption given the powers of a guard and a witness: encrypted data can still be intercepted, and encryption does not prove who sent it - the test is whether the data can still be taken, which it can, so encryption protects meaning, not access or authorship.
