## Algorithms, identifiers and input-process-output

### What an algorithm is

An algorithm is a solution to a problem expressed as a sequence of defined steps. Defined means unambiguous: a follower always knows exactly what the step asks, so 'simmer for 45 minutes' is a step and 'cook until it looks right' is not, because the second depends on the cook's judgement and two followers would stop at different moments. Ordered means the sequence carries the work forward: each step needs what the steps before it produced, so a defined set of steps out of order is as unusable as a vague one in order. Complete means nothing is missing: every case the input can present has a next step waiting for it. Together the three properties make the algorithm transferable: the same input passes through the same steps to the same result, whether the follower is the designer, a stranger, or a processor - which is the whole point, because a solution that only its designer can follow is a solution held in one head, not an algorithm. The everyday test is worth running on any set of steps: hand the steps to someone who has never seen the problem, and watch where they hesitate. Where they ask 'how long?' or 'which one?' or 'what if none arrive?', the step that provoked the question is not yet defined, because a defined step answers its follower's questions in advance. Each such question marks a place where the algorithm still hides its designer's judgement, which is the gap the defined form exists to close.

### Identifier names

The data a problem uses is represented by named constants and variables, and the names are chosen, not stumbled into. A suitable identifier states what the data it holds represents: TotalPrice for a total of money, LoavesSold for a running count, MaxSeats for a capacity that never changes during a run. The name is read by two audiences - the checker confirming the algorithm against the problem, and the next programmer changing it - and both read the name as a claim: TotalPrice had better hold a total of money, because if it holds a count the algorithm's names have lied. The rules of thumb: full words over abbreviations (Quantity beats Qty, because the abbreviation leaves the reader guessing); the kind of thing in the name (Count, Total, Price, Name); and the fixedness in the form - a constant's value is fixed for the whole run, so MaxSeats is written once as a constant and never changed, whereas LoavesSold is a variable that grows as loaves sell. What a name may never do is borrow a keyword or a data type's name: an identifier is a name for data, and DECLARE or INTEGER as a name would collide with the language itself. A habit worth keeping through this whole course: write the identifier first, then write the sentence it claims to hold, and check the two against each other. LoavesSold <- LoavesSold + 1 reads as 'the loaves sold grows by one', and the sentence is true; TotalPrice <- TotalPrice + 1 reads as 'the total price grows by one', and the sentence is only true if a loaf costs exactly one dollar, so the mismatch the reading finds is a real fault caught before the program runs.

### Worked example: input, process, output

Every algorithm has the same three parts, and a small program shows them cleanly. A vet's program works out a dose from an animal's mass: input, the animal's mass in kilograms and the dose rate per kilogram; process, multiply the mass by the rate to get the dose; output, the dose. In pseudocode, with the identifiers chosen for their meaning:

```pseudocode
INPUT BodyMass
INPUT DoseRate
Dose <- BodyMass * DoseRate
OUTPUT "Dose: ", Dose
```

Read the three parts where they sit: the INPUT statements bring the values in, the process step works on them, the OUTPUT statement presents the result. A second example adds one decision to the process - the vet's scale has a maximum:

```pseudocode
INPUT BodyMass
INPUT DoseRate
Dose <- BodyMass * DoseRate
IF Dose > 15 THEN
   Dose <- 15
ENDIF
OUTPUT "Dose: ", Dose
```

Still three parts: the input is unchanged, the process has grown a step, the output is unchanged. Input-process-output is the frame every algorithm in this course hangs on, and the process is where the constructs of the next unit live. A third example adds a repeat to the process, because most real inputs are many: the vet's morning holds a queue of animals, so the input-process-output frame runs once per animal, and the process's steps repeat inside it - which is the loop, the third construct of the next unit, arriving exactly when the input stops being one value and becomes many.

## Constructs, documentation and translation

### The three constructs

Every process ever written in this course is built from three constructs. Sequence: statements run in order, one after the previous, and the order is part of the meaning - Total <- 0 before the loop that adds to Total, because the reverse order destroys the total. Selection: the algorithm chooses between paths. The binary choice is IF ... THEN ... ELSE ... ENDIF; the multi-way choice is CASE OF ... OTHERWISE ... ENDCASE. Iteration: the algorithm repeats steps, in the two forms of 10.2's terms - a count-controlled loop, FOR Counter <- start TO end ... NEXT Counter, when the number of repetitions is known; a conditional loop, WHILE condition ... ENDWHILE, when the repetitions depend on a condition that changes inside the loop, or REPEAT ... UNTIL condition, which tests after the body and so runs it at least once. A worked pair shows the choice: counting a fixed 12 multiples of 7 is FOR work; reading marks until a negative mark arrives is WHILE work, because no count is known - the condition is what ends it. Choosing the construct is the first design decision of any process, because the loop that fits the problem is the loop that ends. The wrong loop shows itself in the ending: a FOR loop reading marks stops after its fixed count whether the marks have run out or not, and a WHILE loop on a condition no statement inside ever changes runs forever, because the loop's ending must be a change the loop itself makes. Ask of every loop 'what ends this?', and ask of every selection 'what if neither branch suits?' - the two questions catch the constructs' two classic faults, a loop that cannot end and a decision that cannot be taken, and both answers must already be in the pseudocode.

### Documenting an algorithm: three languages

The same algorithm can be written in three languages, and each serves a different reader. Structured English: the steps in ordinary sentences, ordered and unambiguous - the form a non-programmer can check against the problem, which is why designs are signed off in it. Pseudocode: the steps in the constructs' exact forms, still language-independent - the form a programmer reads straight into code, which is the working form of this whole course. The flowchart: the steps as boxes and arrows, and the shapes carry meanings every reader shares. A rounded shape is a terminator: START or END. A rectangle is a process: an assignment, a calculation, a defined action. A parallelogram is input or output: values coming in from the world, results going out. A diamond is a decision: a question with exactly two exits, labelled Yes and No, because the follower must know which way each answer goes. The three languages are interchangeable by construction: each English sentence, each pseudocode statement, each flowchart box says one step, so translating between them is statement-by-statement work - and the translation is exactly what the next block practises. The flowchart's shapes earn their keep when a design is argued: two people reading the same boxes see the same paths, because the shapes are the shared vocabulary, and an argument about a diamond is an argument about a decision, not about a drawing style. That is the quiet strength of all three languages - each states the algorithm in a form that carries no argument about the stating.

### Worked example: one algorithm, translated

Take a ride's height rule in structured English: 'Ask the rider's height. If it is less than 120 centimetres, tell them they are too short. Otherwise tell them the ride is allowed.' Translate to pseudocode, statement by statement - the question becomes an INPUT, the condition becomes the IF's condition, the two outcomes become the two branches:

```pseudocode
INPUT Height
IF Height < 120 THEN
   OUTPUT "Too short"
ELSE
   OUTPUT "Ride allowed"
ENDIF
```

Translate the same rule to a flowchart, box by box: a rounded START; a parallelogram INPUT Height; a diamond 'Height < 120?' with its Yes exit to a parallelogram OUTPUT 'Too short' and its No exit to a parallelogram OUTPUT 'Ride allowed'; both output arrows meeting at a rounded END. Now reverse the direction, flowchart to pseudocode, and the boxes hand over their kinds: each parallelogram becomes INPUT or OUTPUT, the diamond becomes IF ... THEN ... ELSE ... ENDIF, the arrows' order becomes the statements' order. One rule, three languages, and nothing of the algorithm gained or lost between them - which is the check to run on any translation: count the decisions, count the paths, and each language must show the same number of each.

## Flowcharts, refinement and logic statements

### Drawing flowcharts

A flowchart is drawn from pseudocode or English construct by construct, because each construct has a box shape waiting for it. Each sequence statement becomes a rectangle with the statement inside and an arrow to the next box. Each input or output becomes a parallelogram. Each selection becomes a diamond with the condition as its question, a Yes arrow to the THEN branch's boxes and a No arrow to the ELSE branch's boxes, the two branches' arrows meeting again after. Each iteration becomes a diamond or a loop of arrows: a WHILE's condition is a diamond before its body, with the No exit leaving the loop and the Yes exit running the body's boxes and an arrow back to the diamond; a FOR's known count becomes the same loop with the counter's question as the diamond. Worked from the previous unit's loop:

```pseudocode
Total <- 0
WHILE Mark >= 0
   Total <- Total + Mark
   INPUT Mark
ENDWHILE
OUTPUT Total
```

Box by box: a rounded START; a rectangle Total <- 0; a parallelogram INPUT Mark; a diamond 'Mark >= 0?' with its No exit to a parallelogram OUTPUT Total and a rounded END, and its Yes exit to a rectangle Total <- Total + Mark, a parallelogram INPUT Mark, and an arrow back to the diamond. The back arrow is the flowchart's whole word for repetition: no new shape is invented, because the arrow that returns is what says 'again'.

### Stepwise refinement

Stepwise refinement is how an English description is produced, and it works from the top down. The problem is written as one statement: 'Produce the shop's day-end report.' That statement is broken into the parts it hides: '1. Read every sale. 2. Compute the day's total. 3. Print the report.' Each of those is broken again - '2. Compute the day's total' into '2.1 Set the day's total to 0. 2.2 For each sale, add its amount to the day's total' - and the breaking continues until every statement is the size of one or two pseudocode statements, which is the level of detail needed to write. The levels are the value: each level can be checked against the problem before the next is broken, so an error found at level 2 costs one line, and the same error found at the end costs a program. Each refinement of a statement is decomposition of that statement - the whole method is 9.1's decomposition applied one break at a time, checked as it goes - and the parts at the bottom level are the modules and statements the program is written from, which is the whole route from a problem in words to a program in pseudocode.

### Logic statements

The conditions that steer a solution are written as logic statements, built with AND, OR and NOT. AND holds when both its sides hold: 'Age >= 13 AND Age <= 19' is true inside the band and false outside, because both bounds must be met. OR holds when at least one side holds: 'Member = TRUE OR Today = "Tuesday"' gives the discount when either reason is present. NOT holds when its statement fails: 'NOT Paid' is true exactly when Paid is FALSE. The three join into the conditions of selections and loops, and each says when its part of the solution acts: the late fee acts 'when the visit is after 17:00 or on a public holiday, and the patient is not exempt' becomes IF (Hour > 17 OR Holiday = TRUE) AND NOT Exempt THEN. The parts of an algorithm solution are defined by these statements - the selection's paths, the loop's end, the module's guard - because a part that acts 'when X and not Y' is defined by exactly that sentence, and the reader who knows the sentence knows the part. A caution that saves marks: the three operators bind differently, so a condition mixing AND with OR needs brackets to say which joins which, because the unbracketed AND grabs its two neighbours and leaves the OR joining the remainder. Write the sentence in English first, then bracket the pseudocode until it says the same thing.

### Common errors

The recurring slip is drawing a decision without its shape or its labels. A decision is a diamond, and its two exits are labelled Yes and No, because the follower must know which way each answer goes; a rectangle with two unlabelled arrows leaves the path to guesswork, which a flowchart exists to prevent. The test: count the exits and read their labels - a decision is a diamond with two labelled exits, and anything else in its place is not a decision.
