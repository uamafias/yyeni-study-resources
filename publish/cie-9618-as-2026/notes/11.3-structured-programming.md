## Procedures, functions and parameters

### Procedures: definition, call, placement

A procedure is a module that does one named job and hands back no value through its name. Its definition:

```pseudocode
PROCEDURE GreetCustomer(Name : STRING)
   OUTPUT "Welcome, ", Name
ENDPROCEDURE
```

The header names the module and its parameters; ENDPROCEDURE closes it. Its call is a statement on its own: CALL GreetCustomer("Anna") - the call does the job, and nothing is left over to assign, because a procedure returns nothing through its name. Where a procedure belongs in the construction of an algorithm is the design question, and it has two answers. Where the same job is needed in several places: printing a receipt header, greeting a caller, drawing a menu border - written once as a procedure and called by name, the job is maintained in one place, so a change to the greeting is a change to one module. Where the program is a long sequence of named steps: a payroll run decomposes into ReadTimes, CalculatePay, PrintPayslips - each step a procedure, the main program reads as the plan, and each module is small enough to check on its own. A procedure is also where the module's job ends with an action rather than an answer - printing, saving, showing - which is the first hint of the procedure-function split that follows. A design habit keeps the placement honest: when a program is planned on paper, each named step of the plan is a candidate module, and the test for candidacy is repetition or length - a step that appears twice in the plan, or a step whose body runs to a page, is written as a procedure and its line in the plan becomes a call. The plan then reads at two levels: the main program as a list of calls, the modules as the detail beneath each - which is exactly the two-level shape 12.2's structure charts draw, arrived at from the writing side.

### Parameters and arguments

A module's values arrive through its parameters - and through nothing else. A parameter is a variable named in the header: PROCEDURE ReportStall(StallName : STRING, TakingsToday : REAL) - and the argument is the value the caller passes in the call: CALL ReportStall("Spices", 435.50). The rule with teeth: the values a module works on arrive through its parameters, so INPUT inside a module is the wrong place for the module's data - the header already holds every value as a parameter, and the call already supplies them. A parameter is passed by value or by reference, and the difference is who owns the variable. By value, the module receives a copy: it may change the parameter inside, and the caller's variable keeps its own value, because the caller handed over a copy. By reference, the module works on the caller's variable itself: a change inside shows outside the call, which is how a procedure that computes an answer can hand it back - write the result into a reference parameter and the caller's variable now holds it. The choice is design: values that only feed the module pass by value, protected from stray changes; values the module must fill in for the caller pass by reference, because the caller is waiting to receive the result. The parameter list is also a contract the caller can check: the number of arguments must match the number of parameters, the types must match in order, and the caller's variable for a reference parameter must exist before the call. A call that passes two arguments to a three-parameter module, or a string where an integer stands in the header, is caught by reading the header alone - which is why the header is called the interface in the next unit's terms: it is where the two sides meet and where every mismatch is visible.

### Functions

A function is a module that computes a single value and hands it back through its name. Its definition:

```pseudocode
FUNCTION AreaOfRoof(Length : REAL, Width : REAL) RETURNS REAL
   DECLARE Area : REAL
   Area <- Length * Width
   RETURN Area
ENDFUNCTION
```

The header names the module, its parameters and the type of the returned value; RETURN inside the body sends the value back and ends the function; ENDFUNCTION closes it. The use is the difference from a procedure: a function is used in an expression - the call is replaced by the returned value - so it is assigned, RoofArea <- AreaOfRoof(6.5, 4.2), tested, IF AreaOfRoof(L, W) > 20 THEN, or joined into a larger expression, and it never follows CALL, because CALL names a job and a function's call is a value. OUTPUT inside a function is the same fault wearing a different coat: the caller needs the value, so the body RETURNs it - displaying it does the caller no good, because OUTPUT goes to the screen and the caller's expression gets nothing. A function is appropriate exactly where a value must be computed and used: the fee for a weight, the average of an array, the larger of two readings - any question the program asks whose answer belongs in an expression. A function also earns its place in a test: because the call is a value, the condition can be written straight against it - IF ParcelFee(Weight) > 50 THEN reads as one question - and a function used in a test is a function that can be reused in a print, a save and a further computation without ever being rewritten. That is the compound interest of returning values: each caller that needs the fee gets it from one module, so the rule itself is stated once and lives once, and every change to the fee - a new threshold, a new rate - is one change in one body.

### Common errors

Three slips recur. OUTPUT where a function must RETURN: the caller needs the value, so the body RETURNs it - the test is whether the calling code needs the value, because a displayed value is nothing to assign. INPUT inside a module: the values arrive through the parameters - the test is the header, because every parameter is already a value. And CALLing a function or assigning a procedure's result: a procedure is CALLed as a statement, a function is used in an expression - the test is whether the module returns a value, because a value-returning module never follows CALL.

## Choosing functions, terminology, efficient pseudocode

### Where a function belongs

The function question in construction is: does this step produce a value the next step uses? A step that answers a question - what is the fee for this weight, is this customer overdrawn, which day sold most - is a function, because the answer belongs where it can be used: in the assignment that stores it, the IF that tests it, the larger expression that continues with it. A step that acts without an answer - print the slip, save the record, sound the alarm - is a procedure, because its job ends with the action. The mistake to avoid is the answer that is computed and then stranded: a program that prints a fee inside the module that computed it has used a procedure for a function’s job, and every later caller that needs the fee quietly cannot have it. The dividing habit: name the step’s output - if the output is a value, the step is a function that RETURNs it; if the output is an action done, the step is a procedure that does it. A boundary worth walking both ways: the same job can be served by either module shape when the caller both needs the value and prints it - a function that returns the fee, with the printing left to the caller, keeps the computation reusable, whereas a procedure that prints the fee bakes the printing in. The reusable arrangement wins the design argument, because a later caller that only tests the fee can join the first caller without either of them changing - which is why the default habit is: compute in functions, act in procedures, and let callers decide what to do with values they are handed.

### The terminology

Four terms travel together and name one thing from four sides. The header is the module’s first line: the name, the parameters, and for a function the return type. The interface is what the caller works from: the header plus what the module does - the deal between the caller and the module, stated in the header and honoured in the body. A parameter is a variable in the header through which a value arrives; an argument is the value the caller passes in the call. The return value is what a function hands back with RETURN - one value, of the declared type, replacing the call in the caller’s expression. And one rule guards all the names: an identifier may not be a keyword, a data type or a built-in function name - DECLARE INTEGER : INTEGER and DECLARE Length : INTEGER both fail, because INTEGER and LENGTH are the language’s own words, and the insert’s function names are part of the language too. One naming habit keeps the interface readable at a distance: the parameters are named for the values they carry - WeightInKg, not W - so the header alone tells a new caller what to pass, and the interface stays legible in every call the program ever writes.

### Efficient pseudocode

Efficient pseudocode is written so that no work is done twice and no repetition is spelled out. Three habits carry it. A job done in several places is written once as a module and called by name - the receipt header printed after every sale is one procedure called three times, not three printed blocks that must be kept alike. A repetition is written as a loop, not as copies - totaling twelve stalls is one loop body, not twelve near-identical lines, because the loop states the shape once. A computed value is stored once and reused - Length(Word) computed four times in one module is one assignment and three uses, because the word did not change in between. Efficiency is also readability, which is the same coin: the short version says the shape once, so the reader checks one statement instead of twelve, and the change that comes later is made in one place - which is what efficient means before it means fast. Efficiency also has a change face worth naming in any justification: the one-module form is cheaper to change, because a job stated once is changed once, and the change is inherited by every caller at the next run - so the efficiency argument in a design discussion is about the writer's work as much as the machine's, and that is the work the next round of changes pays for.

### Common errors

The recurring slip in terminology is a borrowed name. An identifier cannot be a keyword, a data type or a built-in function name such as LENGTH, CHAR or MONTH, because those words are the language’s own - a variable named Length collides with the insert’s function, and a module named Count collides with the register word’s neighbours in a reader’s mind. The test: is the name in the insert or a data type? Choose another.
